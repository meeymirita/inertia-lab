1. Разбор задачи: чему обычно не учат и что заложено в план #

Обычно Inertia знакомятся через starter kit: laravel new, выбрать Vue, и вот уже контроллер возвращает Inertia::render('Dashboard'), а страница появляется. Работает — пока не нужно понять, почему форма после PUT вдруг отправила DELETE, откуда в исходнике страницы взялся хэш пароля или почему после деплоя пользователи видят белый экран. Эта лаба строит блог-платформу Inkwell на Laravel 13 + Inertia 3 + Vue 3 + TypeScript + Pinia с нуля, без starter kit, так чтобы каждый слой «магии» был разобран руками.

💡 Inertia — это протокол, а не фреймворк

Inertia1 не заменяет ни Laravel, ни Vue. Это договорённость о формате общения: первый заход отдаёт обычный HTML с данными страницы внутри, каждый следующий клик — XHR-запрос с заголовком X-Inertia, на который Laravel отвечает JSON-объектом страницы2 (какой компонент показать и с какими props). Клиентская часть подменяет компонент без перезагрузки. Нет клиентского роутера, нет REST API, нет отдельной авторизации на токенах. Пока это не увидено в DevTools, все странности кажутся случайными.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Сессия 1 ставит Inertia руками в чистый Laravel (шаги 1.2–1.3) и разбирает протокол curl-запросами (шаг 1.4): первый визит, Inertia-визит, конфликт версий ассетов, редирект 303.

💡 Props — это публичный API, даже если API «нет»

Всё, что передано в Inertia::render(), уходит в браузер и лежит в исходнике страницы. Передали модель целиком — клиент увидит все её колонки, включая email автора, password (если забыли $hidden) и служебные поля. В SPA+API это было бы очевидной утечкой, в Inertia её легко не заметить: «это же просто данные для шаблона».

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Каждая страница получает данные через API Resources3 с явным списком полей (шаг 2.2). Раздел 5 целиком посвящён тому, что, когда и как отправлять в props.

💡 Pinia дублирует то, что уже прислал сервер

Привычка из SPA: загрузить посты в store и читать их оттуда. В Inertia источник правды для серверных данных — props страницы; при каждом визите они приходят свежими. Скопированные в Pinia, они устаревают после первого же сохранения формы, и начинается ручная синхронизация.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Pinia4 используется только для клиентского состояния, которого нет на сервере: черновик в редакторе с автосохранением в localStorage, настройки чтения (тема, размер шрифта), очередь toast-уведомлений (шаги 4.3, 4.5). Граница проговорена в разделе 2.7.

💡 SSR для блога — не галочка в конфиге

Блогу нужна индексация, значит нужен SSR5. В Inertia 3 он включается почти бесплатно, но ломается на типичных вещах: window в коде компонента, дата, отформатированная по-разному на сервере и в браузере (hydration mismatch6), и самое коварное — Pinia-store, созданный один раз на модуль, который на SSR-сервере становится общим для всех посетителей.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Отдельная сессия 2 про страницу поста, мета-теги и SSR (шаги 3.1–3.4); ловушки разобраны в разделе 8. Студия автора из SSR исключена: ей SEO не нужно.

💡 Формы: 422 не будет, а PUT с файлом не сработает

В Inertia ошибки валидации не приходят как 422 JSON: Laravel делает обычный redirect back, кладёт ошибки в сессию, а Inertia отдаёт их в props errors. Отдельная ловушка — обложка поста: PHP не разбирает multipart/form-data в PUT-запросах, и файл «теряется». И ещё одна: редирект после PUT/PATCH/DELETE должен быть 3037, иначе браузер повторит исходный метод на новом адресе.

РЕШЕНИЕ В ЭТОМ ПЛАНЕ

Раздел 7 разбирает путь формы от useForm до FormRequest и обратно, шаг 4.4 — загрузку файлов с подменой метода, шаг 1.4 — откуда берётся 303.

💡 Каждый partial reload пересчитывает всё

Props, переданные значениями, вычисляются на каждом запросе — даже если клиент попросил обновить только список комментариев. Тяжёлый виджет статистики на дашборде будет пересчитываться при каждом поиске по постам. Shared data из middleware — тем более: она считается на каждом запросе всего приложения.

2. Как Inertia устроен внутри: протокол, объект страницы, визиты #

Вся Inertia держится на одной идее: сервер решает, какую страницу показать и с какими данными; клиент только рисует. Разберём, как это выглядит на проводе.

2.1. Первый визит: HTML с объектом страницы внутри

Браузер открывает /posts/hello-world обычным GET без особых заголовков. Laravel выполняет контроллер, Inertia::render('Posts/Show', [...]) видит, что это не Inertia-запрос, и рендерит корневой Blade-шаблон app.blade.php. Внутри — пустой <div id="app"> и JSON объекта страницы в теге <script type="application/json">. JS-бандл загружается, читает этот JSON, находит компонент Pages/Posts/Show.vue и монтирует его с props. С SSR вместо пустого div приходит уже готовая разметка.

GET /posts/hello-world                          (обычный запрос браузера)
  → web-middleware → HandleInertiaRequests (share, version) → PostController@show
  → Inertia::render('Posts/Show', props)  — запрос НЕ Inertia → рендер app.blade.php
← 200 text/html
   <div id="app"></div>
   <script data-page="app" type="application/json">
     {"component":"Posts/Show","props":{...},"url":"/posts/hello-world","version":"a1b2c3"}
   </script>
   <script type="module" src="/build/assets/app-xxxx.js"></script>

2.2. Следующие визиты: XHR и JSON

Клик по <Link> перехватывается. Клиент Inertia делает XHR на тот же URL с заголовками X-Inertia: true и X-Inertia-Version: a1b2c3. Тот же контроллер, тот же Inertia::render — но теперь ответ application/json с заголовком X-Inertia: true и тем же объектом страницы. Клиент подменяет компонент, делает history.pushState и восстанавливает скролл. Никакого отдельного API: один маршрут обслуживает и HTML, и JSON.

клик <Link href="/posts/other">
  → GET /posts/other   X-Inertia: true   X-Inertia-Version: a1b2c3   X-Requested-With: XMLHttpRequest
← 200 application/json   X-Inertia: true   Vary: X-Inertia
   {"component":"Posts/Show","props":{...},"url":"/posts/other","version":"a1b2c3"}
  → resolve('Posts/Show') → замена компонента (layout не пересоздаётся) → pushState → скролл наверх

2.4. Конфликт версий: 409 и полная перезагрузка

Вы задеплоили новую сборку, а у пользователя открыта вкладка со старым JS. При следующем клике клиент шлёт старый X-Inertia-Version. Middleware сравнивает с текущим, видит расхождение и отвечает 409 Conflict с заголовком X-Inertia-Location. Клиент делает window.location = ... — полную перезагрузку, и браузер получает новые ассеты. Это asset versioning8: без него старый JS пытался бы отрисовать компонент, которого в старом бандле нет.

2.5. Редиректы: почему 303

После PUT /studio/posts/5 контроллер делает redirect()->route('studio.posts.index') — Laravel отвечает 302. По историческим причинам браузеры и XHR при 302 могут повторить исходный метод на новом адресе: получился бы PUT /studio/posts. Middleware Inertia превращает 302 в 303 See Other для PUT/PATCH/DELETE — 303 однозначно означает «теперь сделай GET». Внешние редиректы (на другой домен) делаются через Inertia::location($url): ответ 409 + X-Inertia-Location.

2.6. Partial reload: «пришли только это»

Partial reload9: router.reload({ only: ['comments'] }) отправляет запрос на текущий URL с заголовками X-Inertia-Partial-Component: Posts/Show и X-Inertia-Partial-Data: comments. Laravel выполняет тот же контроллер, но в ответ кладёт только comments. Ключевая тонкость: если prop передан значением, он всё равно вычислился (контроллер выполнился целиком), просто не отправился. Если передан замыканием — не вычислился вовсе. Отсюда правило «тяжёлое — в замыкание» (раздел 5).

Inertia — «современный монолит»: удобство Blade-контроллеров плюс компоненты Vue. Его граница — когда нужен публичный API для мобильного клиента или сторонних интеграций: тогда API пишется отдельно, и Inertia продолжает обслуживать веб.

🔬 Под капотом: как устроен клиентский router.visit, если написать его самому

Упрощённо клиентская часть — это около 60 строк:

async function visit(url, { method = 'get', data, only } = {}) {
  const headers = { 'X-Inertia': 'true', 'X-Inertia-Version': page.version, 'Accept': 'text/html, application/xhtml+xml' }
  if (only) { headers['X-Inertia-Partial-Component'] = page.component; headers['X-Inertia-Partial-Data'] = only.join(',') }
  const res = await xhr(method, url, data, headers)
  if (res.status === 409) return (window.location.href = res.headers['x-inertia-location'])
  if (!res.headers['x-inertia']) return showErrorModal(res.body)   // не Inertia-ответ: ошибка, HTML и т.п.
  const next = JSON.parse(res.body)
  if (only) next.props = { ...page.props, ...next.props }          // слить частичный ответ
  const component = await resolve(next.component)                  // import.meta.glob → Pages/*.vue
  swap(component, next.props)                                       // реактивно заменить корневой компонент
  history.pushState(next, '', next.url)                             // объект страницы — в state истории
  page = next
}
window.addEventListener('popstate', (e) => swap(resolveSync(e.state.component), e.state.props))

Обратите внимание на последнюю строку: при «Назад» клиент не идёт на сервер, а берёт объект страницы из history.state. Отсюда два следствия. Данные страницы лежат в истории браузера — после выхода из аккаунта кнопка «Назад» покажет чужой кабинет, если не включить history encryption (шаг 5.5). И flash-сообщения вынесены из props отдельно, чтобы не всплывать повторно при навигации назад.

5. Props как публичный API: что, когда и как отправлять #

Проблема: «просто данные для шаблона»

В Blade $post живёт на сервере, и шаблон выводит только то, что вы написали в разметке. В Inertia Inertia::render('Posts/Show', ['post' => $post]) сериализует модель в JSON целиком и отправляет в браузер. Всё, что в toArray(), будет в исходнике страницы и в истории браузера: user_id, загруженная связь author с email, черновое поле body, если это тизер в списке. Каждый prop — часть публичного контракта.

Решение 1: явная форма данных через API Resources

Для каждой «формы» данных — свой ресурс: PostCardResource для карточки в ленте (заголовок, анонс, обложка, автор, теги — без тела), PostResource для страницы поста (с HTML тела), UserResource — только id, name. Ресурс — это белый список, как select в Prisma или DTO на выходе. Плюс ресурсы дают типы: TypeScript-интерфейсы в types/models.ts описывают ровно то, что отдаёт ресурс.

Решение 2: правильный тип prop под задачу

Решение 3: shared data — минимум и лениво

Shared data10 — HandleInertiaRequests::share() — выполняется на каждом Inertia-запросе. Туда кладут только то, что нужно почти каждой странице (текущий пользователь в форме UserResource, имя приложения), и только замыканиями. «Количество непрочитанных комментариев» в shared data — это лишний SQL-запрос на каждый клик по сайту; правильнее — defer на тех страницах, где счётчик показывается.

🔬 Под капотом: что именно видно в браузере и почему $hidden недостаточно

Откройте любую страницу с props и посмотрите исходный код (view-source:): JSON объекта страницы лежит в теге <script type="application/json">. Тот же JSON — в ответах XHR на вкладке Network и в history.state каждой посещённой страницы (в консоли: history.state).

$hidden на модели защищает от худшего (пароль, remember_token), но работает по чёрному списку: новая чувствительная колонка (stripe_customer_id, internal_notes) по умолчанию окажется публичной. Ресурс работает по белому списку — новая колонка не уйдёт, пока вы её явно не добавите. Вторая проблема моделей — связи: $post->load('author') отдаст автора со всеми видимыми полями, включая email; в ресурсе автор проходит через UserResource.

И третья, про производительность: модель сериализует атрибуты, которые фронтенду не нужны. Тело поста на 20 КБ в каждой карточке ленты из 20 карточек — это 400 КБ JSON на одну страницу.

7.1. Путь отправки формы

useForm({ title, body, cover }).post(store.url(), { forceFormData: true })
  → POST /studio/posts   X-Inertia: true   X-XSRF-TOKEN: ...   multipart/form-data
  → VerifyCsrfToken → auth → StorePostRequest::rules()
       ├── ошибка → ValidationException → redirect()->back() (302) + errors во flash-сессии
       │     → клиент следует редиректу (GET /studio/posts/create, X-Inertia)
       │     → HandleInertiaRequests кладёт errors в props → form.errors.title = "..."
       │       (страница та же, состояние формы сохранено: preserveState для неуспешных визитов)
       └── успех → Post::create → Inertia::flash('toast', ...) → redirect()->route('studio.posts.edit', $post)
             → GET /studio/posts/12/edit → новый компонент, form.wasSuccessful = true

Ключевое отличие от API: валидация не отвечает 422. Laravel видит, что это не JSON-запрос (X-Inertia, а не Accept: application/json), и делает классический redirect back с ошибками в сессии — ровно как для Blade-формы. Middleware Inertia берёт ошибки из сессии и кладёт их в shared prop errors. Поэтому вся валидация пишется один раз — в FormRequest — и на фронте не дублируется.

7.3. Error bags и несколько форм на странице

На странице поста две формы: комментарий и (у редактора) быстрая модерация. Если обе пишут ошибки в общий errors, ошибка поля body одной формы покажется в другой. Опция errorBag: 'comment' (error bag12) кладёт ошибки в errors.comment.body — изолированное пространство имён.

7.4. Файлы и подмена метода

Если в данных формы есть File, Inertia автоматически отправит multipart/form-data. Но PHP разбирает multipart только для POST. Для обновления поста с новой обложкой отправляют POST с полем _method: 'put' — Laravel увидит его и маршрутизирует как PUT (method spoofing13). Это не баг Inertia и не баг Laravel — так устроен PHP.

🔬 Под капотом: почему состояние формы не теряется после редиректа с ошибками

Неуспешная отправка технически — это новый визит: 302 → GET той же страницы → новый объект страницы. Если бы клиент пересоздал компонент, всё введённое пропало бы. Inertia по умолчанию сохраняет состояние компонента (preserveState), когда в ответе есть ошибки, — компонент тот же, его локальное состояние (и useForm) живо, обновились только props. При успешном визите на другой компонент состояние, естественно, сбрасывается.

Ещё одна деталь: form.processing в Inertia 3 сбрасывается в onFinish, то есть когда визит полностью завершён, включая следование редиректу. Кнопка остаётся заблокированной до появления новой страницы — двойной клик не отправит форму дважды.

8.1. Как работает SSR в Inertia

GET /posts/hello-world  (первый визит, бот поисковика или человек)
  → Laravel: контроллер → объект страницы
  → Inertia: HTTP POST объекта на SSR-сервер (Node; в dev — эндпоинт Vite-плагина)
  → Node: createInertiaApp + renderToString → { head: [...теги], body: "<div id=app>...готовый HTML...</div>" }
  → Laravel вставляет head и body в app.blade.php
← HTML с контентом и мета-тегами  → браузер показывает текст сразу
  → JS загружается → hydration: Vue «прикрепляется» к готовой разметке, не перерисовывая её

Если SSR-сервер недоступен или упал при рендере, Inertia молча возвращает обычную клиентскую страницу — сайт работает, но поисковик видит пустой div. Поэтому в тестах включают throw_on_error, а в проде проверяют php artisan inertia:check-ssr.

8.3. Мета-теги

Компонент <Head> управляет <title> и <meta> на клиенте, а при SSR его содержимое попадает в HTML. Атрибут head-key предотвращает дубли: description из layout заменяется description страницы, а не добавляется вторым тегом. Для блога нужны title, description, canonical, OpenGraph (og:title, og:image) — превью ссылок в мессенджерах берутся оттуда, и мессенджеры JavaScript не выполняют.

8.4. Когда SSR не нужен

Студии автора индексация не нужна, её страницы под авторизацией, а редактор тянет браузерный код. SSR для неё — только затраты (CPU на Node, риск ошибок). Поэтому /studio/* исключены через withoutSsr, и на этих страницах можно спокойно пользоваться window.

🔬 Под капотом: почему Pinia на уровне модуля утекает между посетителями

В браузере модуль JavaScript выполняется один раз на вкладку — один пользователь, один store, всё хорошо. SSR-сервер — это долгоживущий процесс Node, который рендерит страницы для всех посетителей подряд. Модуль app.ts загружается в нём один раз, и const pinia = createPinia() на верхнем уровне создаёт один store на весь сервер. Посетитель A записал в store своё имя — посетитель B получил разметку с именем A.

Inertia 3 вызывает withApp(app) для каждого рендера, поэтому app.use(createPinia()) внутри него даёт свежий store на каждый запрос. Это и есть главная причина правила из раздела 2.7: в Pinia не кладут данные пользователя с сервера — они и так приходят в props, и они не должны храниться ни в каком общем месте.

🔬 Под капотом: Vary: X-Inertia и почему без него ломается кэш

Один URL отдаёт то HTML, то JSON в зависимости от заголовка. Если между браузером и сервером стоит кэш (CDN, Nginx, сам браузер при «Назад» после закрытия вкладки), он должен знать, что ответ зависит от X-Inertia, иначе может отдать сохранённый JSON на обычный заход — и пользователь увидит сырой JSON вместо страницы. Заголовок Vary: X-Inertia сообщает кэшам: «храните варианты отдельно по этому заголовку». Middleware ставит его автоматически.

X-Requested-With: XMLHttpRequest клиент Inertia тоже отправляет — благодаря ему $request->ajax() в Laravel возвращает true, а обработчик исключений в режиме отладки отдаёт HTML-страницу ошибки, которую Inertia покажет в модальном окне.

class Post extends Model
{

    // status и published_at намеренно не fillable: их меняют только явные действия

    protected function casts(): array

            'status' => PostStatus::class,
            'published_at' => 'datetime',
        ];
    }

    public function author(): BelongsTo
    {
        return $this->belongsTo(User::class, 'user_id');
    }

    public function tags(): BelongsToMany
    {
        return $this->belongsToMany(Tag::class);
    }

    public function comments(): HasMany
    {
        return $this->hasMany(Comment::class);
    }

    public function likers(): BelongsToMany
    {
        return $this->belongsToMany(User::class, 'post_likes')->withTimestamps();
    }

    public function scopePublished(Builder $query): void
    {
        $query->where('status', PostStatus::Published)->where('published_at', '<=', now());
    }

    public function isPublished(): bool
    {
        return $this->status === PostStatus::Published && $this->published_at?->isPast();
    }

    /** Комментарии, которые может видеть $viewer: одобренные + свои; редактор видит все */
    public function commentsVisibleTo(?User $viewer): HasMany
    {
        return $this->comments()
            ->with('author:id,name')
            ->when($viewer?->role !== Role::Editor, function (Builder $q) use ($viewer) {
                $q->where(fn (Builder $q) => $q->whereNotNull('approved_at')
                    ->when($viewer, fn (Builder $q) => $q->orWhere('user_id', $viewer->id)));
            })
            ->oldest();
    }

    public function coverUrl(): ?string
    {
        return $this->cover_path ? Storage::disk('public')->url($this->cover_path) : null;
    }
}

Если enum расширится, а TS-тип нет — фронтенд не узнает о новом статусе, это та самая точка ручной синхронизации из заметки в начале раздела.

$fillable — это защита mass assignment на уровне модели. Форма регистрации, где кто-то дописал role=editor, не сделает его редактором, даже если контроллер по ошибке передаст все поля запроса. Две линии обороны: FormRequest пропускает только перечисленные поля, модель — только fillable.

🔬 Под капотом: как Inertia превращает ресурс в props и откуда берётся N+1

Inertia при сборке ответа проходит по props: замыкания вызывает, а для JsonResource вызывает toResponse($request)->getData(true) — то же самое, что вернул бы API-контроллер. Поэтому пагинированная коллекция приходит в форме { data, links, meta }, знакомой по Laravel API.

whenLoaded('author') отдаёт автора, только если связь загружена через with(). Без with поле просто пропадёт, а не вызовет ленивую загрузку на каждую карточку (10 карточек = 10 лишних запросов). Защититься от случайного N+1 можно глобально: Model::preventLazyLoading(! app()->isProduction()) в AppServiceProvider — ленивая загрузка в dev будет бросать исключение. 🔬 Под капотом: почему v-html опасен и что ещё может пойти не так с Markdown

v-html вставляет строку как HTML без экранирования. Если в строке окажется <img onerror> или <script> (скрипты через innerHTML не выполняются, но обработчики событий — да), код выполнится в контексте сайта: сможет делать запросы от имени пользователя, читать props текущей страницы. В Inertia это особенно неприятно: все запросы клиента автоматически несут сессионную cookie и XSRF-токен.

Варианты защиты в порядке надёжности: (1) не допускать HTML на входе (наш strip), (2) санитайзер на сервере по белому списку тегов (например, HTMLPurifier), если HTML в постах нужен, (3) Content-Security-Policy как вторая линия. Санитизация на клиенте (DOMPurify) полезна, но при SSR её приходится выполнять и на сервере.

Производительность: Str::markdown на каждый просмотр — лишняя работа. В Production Hell одно из заданий — хранить готовый HTML в колонке и пересчитывать его при сохранении.

🔬 Под капотом: как Inertia управляет head и что такое data-inertia

На клиенте компонент <Head> регистрирует свои дочерние теги в общем менеджере; при каждом визите менеджер собирает теги всех смонтированных <Head> (layout + страница), дедуплицирует по head-key (страница побеждает layout, так как монтируется позже) и синхронизирует их с реальным document.head. Управляемые теги помечаются атрибутом data-inertia (в Inertia 2 он назывался inertia) — так менеджер отличает свои теги от статических тегов шаблона и не трогает последние.

При SSR те же теги рендерятся на сервере в массив строк и вставляются <x-inertia::head> в HTML. Содержимое слота <x-inertia::head> (запасной <title>) выводится только когда SSR не активен — поэтому дублей <title> нет.

🔬 Под капотом: optional, defer и WhenVisible — в чём разница

Inertia::optional — «никогда не присылай, пока явно не попросят через only». Кто попросит — решает клиент: кнопка, вкладка, WhenVisible. Inertia::defer — «не присылай в первом ответе, но клиент сам сразу дозапросит после отрисовки»: страница видна быстро, данные догружаются без участия пользователя (шаг 5.3).

WhenVisible внутри использует IntersectionObserver: когда элемент приближается к области видимости на buffer пикселей, выполняется router.reload({ only: ['comments'] }). При SSR сервер рендерит fallback — для комментариев это правильно: поисковику они не нужны, а HTML легче. Если комментарии нужно индексировать (форум, Q&A), их передают обычным prop.

🔬 Под капотом: как работает CSRF в Inertia без мета-тега

Laravel на каждом ответе ставит cookie XSRF-TOKEN18 (зашифрованное значение CSRF-токена, без флага HttpOnly). HTTP-клиент Inertia перед каждым запросом читает эту cookie и отправляет её значение в заголовке X-XSRF-TOKEN; middleware ValidateCsrfToken расшифровывает и сверяет. Чужой сайт не может прочитать cookie вашего домена — значит, не может подставить заголовок.

Поэтому мета-тег <meta name="csrf-token"> в корневой шаблон Inertia-приложения не добавляют: значение в нём фиксируется при первой загрузке страницы, а после regenerateToken() (выход, вход) устаревает — и следующий POST получит 419. Cookie же обновляется с каждым ответом.

Ошибка 419 (токен устарел, например после долгого простоя) — не Inertia-ответ, поэтому клиент показывает её в модальном окне. Как превратить её в аккуратное сообщение — задание в Production Hell.

import { defineStore } from 'pinia'
import { ref } from 'vue'

export type ToastType = 'success' | 'error' | 'info'
export interface Toast {
    id: number
    type: ToastType
    message: string
}

export const useUiStore = defineStore('ui', () => {
    const toasts = ref<Toast[]>([])
    let seq = 0

    function push(toast: { type: ToastType; message: string }, ttlMs = 4000): void {
        const id = ++seq
        toasts.value.push({ ...toast, id })
        if (typeof window !== 'undefined') window.setTimeout(() => dismiss(id), ttlMs)
    }

    function dismiss(id: number): void {
        toasts.value = toasts.value.filter((t) => t.id !== id)
    }

    return { toasts, push, dismiss }
})

🔬 Под капотом: что происходит с оптимистичным состоянием при гонке кликов

При вызове optimistic() Inertia сравнивает возвращённый объект с текущими props и делает снимок только изменившихся ключей (post), затем применяет изменение и отправляет запрос. Успех — props заменяются ответом сервера (истиной). Ошибка (500, 422, сеть) — откатываются только ключи из снимка.

Если пользователь кликнул трижды быстро, в полёте три запроса; Inertia отслеживает, какие ключи трогал каждый, и не даёт ответу раннего запроса перезаписать оптимистичное состояние, пока не завершится последний. Но сервер выполнит toggle() три раза — итог «лайкнуто», хотя пользователь видел три переключения. Toggle по природе не идемпотентен; надёжнее явные «поставить» и «снять» (PUT/DELETE) — задание в Production Hell.

    а: 'a', б: 'b', в: 'v', г: 'g', д: 'd', е: 'e', ё: 'e', ж: 'zh', з: 'z', и: 'i', й: 'y', к: 'k', л: 'l',

export function slugify(input: string): string {
    return input
        .toLowerCase()
        .split('')
        .map((ch) => map[ch] ?? ch)
        .join('')
        .replace(/[^a-z0-9]+/g, '-')
        .replace(/^-+|-+$/g, '')
        .slice(0, 180)
}

export interface LocalDraft {
    title: string
    slug: string
    excerpt: string
    body: string
}

const storageKey = (id: number | 'new') => `inkwell:draft:${id}`

export const useEditorStore = defineStore('editor', () => {
    const lastSavedAt = ref<number | null>(null)

    function load(id: number | 'new'): LocalDraft | null {
        if (typeof window === 'undefined') return null
        const raw = window.localStorage.getItem(storageKey(id))
        return raw ? (JSON.parse(raw) as LocalDraft) : null
    }

    function save(id: number | 'new', draft: LocalDraft): void {
        window.localStorage.setItem(storageKey(id), JSON.stringify(draft))
        lastSavedAt.value = Date.now()
    }

    function clear(id: number | 'new'): void {
        window.localStorage.removeItem(storageKey(id))
        lastSavedAt.value = null
    }

    return { lastSavedAt, load, save, clear }
})

🔬 Под капотом: почему PUT с файлом не работает и что делает forceFormData

Обход стандартный: отправить POST, а метод передать полем _method=put — Laravel до маршрутизации подменит метод запроса (method spoofing). Inertia 3 документирует это ограничение прямо.

forceFormData: true отправляет multipart всегда, даже если файл не выбран. Без него запрос без файла ушёл бы JSON-ом, а с файлом — multipart; поведение одинаково, но с forceFormData оно предсказуемо. 🔬 Под капотом: preserveState, preserveScroll, replace — что именно каждый сохраняет

preserveState — не пересоздавать компонент страницы, а обновить ему props: локальные ref, useForm, раскрытые элементы остаются. По умолчанию false для обычных визитов (переход на другую страницу должен начинаться с чистого листа) и true для неуспешной отправки формы.

preserveScroll — не прокручивать наверх. replace — history.replaceState вместо pushState: кнопка «Назад» уведёт со страницы поиска, а не пройдёт по каждой введённой букве.

Inertia::once работает через метаданные объекта страницы: клиент запоминает значение и при следующих визитах сообщает серверу, что оно у него есть — сервер пропускает вычисление. Значение живёт, пока пользователь на сайте; для справочников, которые меняются редко, это идеально.

Время кэша — осознанный компромисс; есть и инвалидация кэша по тегам (cacheTags) после действий.

Polling тратит запрос даже тогда, когда ничего не изменилось. При сотне редакторов и интервале 15 с это ~7 запросов в секунду — пустяк. При тысячах пользователей и интервале в секунду (чат, совместное редактирование) нужен push: Laravel Reverb + Echo, и по событию — router.reload({ only: [...] }). Inertia сам не держит соединений, но отлично сочетается с WebSocket: сервер шлёт «что-то изменилось», клиент перезапрашивает нужные props.

Почему useHttp, а не router.get: Inertia-визит ожидает ответ-страницу. JSON-ответ без X-Inertia клиент воспримет как ошибку и покажет модальное окно. Граница простая: ответ — страница → router/Link/useForm; ответ — данные → useHttp.

🔬 Под капотом: как устроено шифрование истории

Когда ответ помечен encryptHistory, клиент перед записью в history.state шифрует объект страницы ключом, который хранится в sessionStorage (Web Crypto API, AES-GCM). Inertia::clearHistory() в ответе говорит клиенту: удалить ключ и сгенерировать новый. Старые записи истории остаются зашифрованными мусором; при попытке вернуться к ним расшифровка не удаётся, и клиент делает обычный визит на сервер — а тот уже видит гостя.

Шифрование требует безопасного контекста (HTTPS или localhost) и стоит немного CPU на каждый визит. Поэтому его включают не везде, а на страницах с чувствительными данными — студия, личный кабинет, админка. Глобально его можно включить в config/inertia.php.

11. Глоссарий терминов #

В порядке первого появления в тексте.

1. Inertia ↩ — протокол и набор адаптеров (серверный для Laravel, клиентский для Vue/React/Svelte), позволяющий строить SPA с серверной маршрутизацией и контроллерами, без отдельного API.

2. Объект страницы ↩ — JSON {component, props, url, version, ...}, который сервер отдаёт на каждый визит: внутри HTML при первом заходе и как тело ответа при Inertia-визите.

3. API Resource ↩ — класс Laravel (JsonResource), описывающий, какие поля модели и в каком виде попадут в JSON. Работает как белый список полей.

4. Pinia ↩ — официальная библиотека состояния Vue. В Inertia-приложении — только для клиентского состояния, которого нет на сервере.

5. SSR (Server-Side Rendering) ↩ — рендеринг Vue-страницы в HTML на сервере (Node), чтобы браузер, поисковик и мессенджер сразу получили контент.

6. Hydration (гидрация) ↩ — процесс, при котором клиентский Vue «оживляет» готовую серверную разметку, не пересоздавая DOM. Mismatch — расхождение серверной и клиентской отрисовки.

7. 303 See Other ↩ — код редиректа, однозначно требующий выполнить GET по новому адресу. Inertia подменяет им 302 после PUT/PATCH/DELETE.

8. Asset versioning ↩ — механизм, при котором клиент сообщает версию своих ассетов, а сервер при расхождении отвечает 409 и заставляет браузер полностью перезагрузить страницу.

9. Partial reload ↩ — Inertia-запрос на текущую страницу с заголовками X-Inertia-Partial-Component/-Data: сервер отдаёт только перечисленные props.

10. Shared data ↩ — props, которые HandleInertiaRequests::share() добавляет к каждой странице (пользователь, имя приложения, ошибки).

11. Policy ↩ — класс Laravel с правилами доступа к модели (view, update, publish...). Вызывается через Gate::authorize, can, middleware can:.

12. Error bag ↩ — именованное пространство ошибок валидации (errors.comment.body), чтобы ошибки нескольких форм на странице не смешивались.

13. Method spoofing ↩ — передача HTTP-метода полем _method в POST-запросе. Нужна, когда метод PUT/PATCH/DELETE нельзя отправить напрямую (HTML-формы, multipart в PHP).

14. Persistent layout ↩ — layout, экземпляр которого Inertia сохраняет между визитами: меняется только страница внутри, состояние layout живёт.

15. Laravel Wayfinder ↩ — генератор TypeScript-функций для маршрутов и контроллеров Laravel; переименование маршрута становится ошибкой компиляции.

16. XSS (межсайтовый скриптинг) ↩ — внедрение исполняемого кода в страницу через данные (например, HTML в тексте поста), который выполняется в браузере других пользователей.

17. Session fixation ↩ — атака, при которой злоумышленник заранее подсовывает жертве известный id сессии; лечится сменой id после входа (regenerate).

18. CSRF и XSRF-TOKEN ↩ — защита от подделки запросов с чужих сайтов: Laravel ставит cookie XSRF-TOKEN, клиент Inertia возвращает её в заголовке X-XSRF-TOKEN.

19. Flash data ↩ — одноразовые данные ответа (Inertia::flash), которые не сохраняются в истории браузера и не всплывают при «Назад».

20. Оптимистичное обновление ↩ — изменение UI до ответа сервера в расчёте на успех; при ошибке Inertia восстанавливает сохранённый снимок props.

21. Merge props ↩ — props, которые при partial reload добавляются к уже загруженным данным, а не заменяют их. Основа «показать ещё» и бесконечной ленты.

22. Prefetch ↩ — предварительная загрузка страницы (при наведении, монтировании) с кэшированием ответа на клиенте.

23. Deferred props ↩ — props, которые не входят в первый ответ: клиент запрашивает их сам сразу после отрисовки, сгруппированными запросами.

24. Polling ↩ — периодический повторный запрос данных по таймеру; в Inertia — usePoll с partial reload.

25. useHttp ↩ — хук Inertia 3 для запросов к JSON-эндпоинтам без визита: состояние processing/errors, отмена, оптимистичные обновления.

26. History encryption ↩ — шифрование объекта страницы перед записью в history.state ключом из sessionStorage; после clearHistory старые записи нечитаемы.
